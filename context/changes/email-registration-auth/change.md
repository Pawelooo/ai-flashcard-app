## Notes

- Confirmed during planning: Fly.io production has real registered users, all with blank `email` (current registration only ever collected `username`). This ruled out a destructive reset and drove the data-preserving `AUTH_USER_MODEL` migration approach in Phase 1.
- Scope grew from "register + verify + login" to include password reset — user explicitly asked to bundle it since it shares the same email/token infrastructure.
- Plan review (2026-07-28, see `reviews/plan-review.md`): found and fixed 3 critical gaps in the plan before implementation — (1) new email-only registrations would collide on `username=''` after the second signup, fixed by making `username` nullable via the same blank→NULL pattern used for `email`; (2) `flashcards/tests.py` and `verify_manual_checks.py` import the concrete (soon-to-be-swapped) `auth.models.User` directly, which would break `manage.py test`; (3) no `accounts/admin.py` was planned, which would have broken the admin's Users page (used for content seeding) after the `AUTH_USER_MODEL` swap. Two lower-priority items (nav/leaderboard `username` display, missing e2e coverage for registration) were accepted as risks for implementation time.
- **2026-08-08, Phase 1 landed (commit `45df554`).** Along the way, discovered and fixed two things not called out in the plan: (a) local/prod databases that already had `admin.0001_initial` applied before `accounts` existed hit `InconsistentMigrationHistory` on `migrate` — fixed via `accounts.management.commands.bootstrap_custom_user`, which records `accounts.0001_initial` as applied (it's a no-op `SeparateDatabaseAndState`, so this is safe) before the real `migrate` runs. **Must be run once against Supabase prod before its first `migrate` under this change**, same as it was run against local `db.sqlite3`. (b) `CustomUser`'s email uniqueness collided across `create_user()` calls that omit an email, because `BaseUserManager.normalize_email(None)` returns `''` not `None` — fixed with `CustomUserManager.normalize_email` overridden to keep it `None`.
- **Local dev machine has two unrelated TLS quirks, both confirmed prod-safe via a `python:3.14-slim` Docker container (production's actual base image) — do not chase these as code bugs:** (1) AVG's "Web/Mail Shield" intercepts outbound TLS with its own re-signed cert, breaking verification until disabled per-session; (2) even with AVG off, the local `uv`-managed CPython 3.14.2 Windows build crashes (`OPENSSL_Uplink: no OPENSSL_Applink`) on any real TLS handshake (reproduced even outside Django, e.g. plain `ssl.wrap_socket` to google.com) — a bug in that specific Windows interpreter build, not in this project's code. Real email sending must be verified either in the Docker container or after deploy, not via native `manage.py runserver` on this machine.
- **Phase 2 status at pause:** all automated Progress items (2.1–2.7) done and committed-pending (not yet committed — will land with Phase 2's own phase-end commit). Manual items 2.8/2.9 (real-inbox register→verify→auto-login round trip, UI sanity of check-email/verify-failed screens) still open — was mid-way through verifying via a Docker container (`docker run ... naukaai-emailtest`, port 8000) to route around the two TLS quirks above when paused. Also found and fixed along the way: local `.env` was missing `DEFAULT_FROM_EMAIL`, which made Resend reject sends with the settings.py placeholder `noreply@localhost` (550 Invalid `from` field) — user added `DEFAULT_FROM_EMAIL=NaukaAI <onboarding@resend.dev>` to `.env`. To resume: rebuild/rerun the `naukaai-emailtest` Docker image (already built with current Phase 2 code) and complete the real-inbox round trip via `http://localhost:8000`.
